# Project Tracking P1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the P1 Project Tracking app: a Go `tracking-service` and Next.js `/tracking` pages. It runs locally on an in-memory store, and the owner later plugs in PostgreSQL.

**Architecture:**
- **Backend:** Go service `tracking-service` on `chi`.
  - Modules `project`, `board` and `card` hold the rules and permission checks.
  - They talk only to the interfaces in `internal/store`.
  - `internal/store/memory` implements those interfaces today. The owner writes the PostgreSQL implementation later.
- **Frontend:** a minimal Next.js host app for local dev.
  - The part that moves into the existing web app is `app/tracking/**`.
  - The browser calls `/api/tracking/v1/*` on its own origin. Next.js rewrites the call to the Go service.

**Tech Stack:**
- **Backend:** Go 1.27, `github.com/go-chi/chi/v5`, `log/slog`.
- **Frontend:**

  - Tooling: `openapi-typescript` 7.13, `vitest` 5.1 + Testing Library.

## Global Constraints

- **No PostgreSQL code, SQL or migrations anywhere.** Data access goes through `internal/store` interfaces only.
- **`X-User-ID` auth:**
  - It is compiled only with `-tags local`.
  - `main` exits with an error if `ENV=local` runs on a build without that tag.
  - `main` also exits if `ENV` is anything else and no production authenticator is wired.
- **Ids:** every id is `int64`, including user ids, which come from user-service.
- **Priority:** stored as `int16` 0–3. The API uses only `"low" | "medium" | "high" | "urgent"`.
- **Status and roles:**
  - Project status: `active | on_hold | done`. Archive is `archived_at` only.
  - Project roles: `pm | member | viewer`. System roles (`user_roles`): `admin | manager`.
- **Response envelope:**
  - Success: `{ "success": true, "data": ... }`.
  - Failure: `{ "success": false, "error": "<english>", "code": "<code>", "fields"?: {"<field>": "<code>"} }`.
- **Error codes and HTTP status:**

  | Code | Status |
  |---|---|
  | `bad_request` | 400 |
  | `unauthorized` | 401 |
  | `forbidden` | 403 |
  | `not_found` | 404 |
  | `conflict` | 409 |
  | `validation_failed` | 422 |
  | `server_error` | 500 |

  The client adds `network_error` for a request with no response.
- **Length limits:** counted in runes (`utf8.RuneCountInString`) after trimming.

  | Field | Max |
  |---|---|
  | Project name, card title | 200 |
  | `description_md` | 20,000 |
  | Comment body | 5,000 |
  | Checklist text | 500 |
  | List name | 100 (builder's call) |
  | Label name | 40 (builder's call) |

  Names, titles and texts must not be empty.
- **Dates:** `YYYY-MM-DD`. Rules: `end >= start` and `due >= start`.
- **Base path:** `/api/tracking/v1`.
- **Every write:**
  - runs in one `store.Update` transaction;
  - appends an activity event;
  - bumps `boards.updated_at` when it changes what the board shows (lists, cards, assignees, card labels, checklist, comments, labels, members);
  - bumps `cards.updated_at` when it writes a card's child;
  - returns the updated entity.
- **Frontend strings:** every user-facing string, `aria-label`, `title` and `placeholder` comes from a per-component `TEXT = { th, en }`. User content is never translated.
- **Frontend data:** no `router.push` for page changes, no raw hex colours in components, and no success toast for drags or inline edits.
- **Frontend portability:** tracking pages are `'use client'` and read params with `useParams()` / `useSearchParams()`. They import shadcn parts from `@/components/ui/*`. This keeps them portable to the host app's Next version.
- **Commits:** one commit per task, Conventional Commits, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Stale move neighbours:** the client's cache is older than the server, so `beforeId`/`afterId` are no longer in the target list, or no longer ordered. The server must answer `conflict` and must not write a wrong order. The client then refetches the board. Tests: Task 6 and Task 15.
2. **Child-route access without membership:** `/cards/{id}`, `/checklist/{id}`, `/comments/{id}`, `/labels/{id}` and `/lists/{id}` must resolve their project and answer `not_found` to a non-member. They must never answer with data. Tests: Tasks 4–9.
3. **Archived parents:**
   - Creating a card in an archived list, moving a card into one, or adding a checklist item or comment to an archived card answers `conflict`.
   - Restoring a card whose list is archived answers `conflict`.
   - Tests: Tasks 5, 6, 8, 9.
4. **Thai text and emoji at the length limit:** a 200-rune Thai title passes, 201 runes fails. Byte length is never used. Tests: Task 6.
5. **Last PM:** removing or demoting the only PM answers `conflict`, also when the PM does it to themselves. An admin who is not a member is not counted as a PM. Tests: Task 4.

### Task 2: LexoRank keys

**Files:**
- Create: `backend/internal/rank/rank.go`
- Test: `backend/internal/rank/rank_test.go`

**Interfaces:**
- Produces:
  - `rank.Between(a, b string) (string, error)`. An empty `a` means "start" and an empty `b` means "end". The result satisfies `a < key < b` under byte comparison (`COLLATE "C"`).
  - `rank.ErrNoGap`: returned when `a >= b` (with both non-empty), or when the result would be longer than 48 bytes.
  - `rank.Spread(n int) []string`: `n` ascending keys of equal length, evenly spaced. Used for rebalancing and seeding.

Algorithm:
- Alphabet `0123456789abcdefghijklmnopqrstuvwxyz`. A key never ends in `'0'`, so there is always room below it.
- Walk both keys digit by digit, treating a missing digit of `a` as `0` and a missing digit of `b` as `36`.
- Copy the common prefix. At the first position where the digits differ by 2 or more, emit their midpoint and stop. Otherwise emit `a`'s digit and keep going with an open upper bound.

- [ ] **Step 1: Write failing tests:**
  - `TestBetween_OpenEnds`: `Between("","")` returns a non-empty key.
  - `TestBetween_Ordering`: for 1,000 random pairs taken from successive inserts (front, back and middle), `a < k < b`.
  - `TestBetween_NeverEndsInZero`.
  - `TestBetween_SameKeyIsNoGap`: `Between("m","m")` returns `ErrNoGap`, and so does `Between("n","m")`.
  - `TestBetween_RepeatedInsertAtSameSpotHitsNoGapEventually`: insert repeatedly between the same left key and the newest key until `ErrNoGap` comes back. No key may exceed 48 bytes.
  - `TestSpread`: `Spread(5)` is strictly ascending, all keys have equal length, and none ends in `'0'`.
